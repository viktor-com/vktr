# ADR 0001: Base codebase for `vktr`

- Status: Accepted
- Date: 2026-09-20
- Deciders: vktr maintainers

## Context

`vktr` must be a coding TUI at parity with Claude Code, Codex, OpenCode, Grok Build and pi,
with Viktor as a first-class provider. The brief named Grok Build (xAI's `grok` TUI) as the
preferred base and OpenCode (MIT) as the fallback if Grok Build cannot legally or practically be
repackaged. This ADR records the evidence gathered on 2026-09-20 and the decision.

## Evidence: Grok Build

**Source availability.** The full Rust source is public at
`github.com/xai-org/grok-build` (default branch `main`, `SOURCE_REV`
`9bb727ccdff0a793ee73bcde4e2e09cbef6b5387`, pushed 2026-09-19). It is "synced periodically from
the SpaceXAI monorepo". The workspace has 162 members: `crates/codegen/xai-grok-*` (TUI,
agent runtime, tools, sampler, MCP, sessions), `crates/common/*`, `crates/build/*`,
`third_party/` (vendored Mermaid stack). The installed binary (`grok 1.0.30`, a 160 MB static
ELF) embeds the same crate paths (`crates/codegen/xai-grok-shell`, `xai-grok-pager`,
`xai-grok-tools`, ...), so the published tree is the shipped product, not a subset.
`CONTRIBUTING.md`: no external PRs; the tree is "published for source transparency and local
builds". That is fine for a fork; it means upstream tracking is a periodic re-vendor.

**License.** `LICENSE` is Apache License 2.0 (copyright 2023-2026 SpaceXAI). It permits
forking, modification, redistribution and commercial use. Obligations that bind `vktr`:
§4 keep the LICENSE and attribution notices, mark modified files / state changes (we add a
`NOTICE` and keep `THIRD-PARTY-NOTICES`); §6 grants **no trademark rights**, so the fork must
not ship under the "Grok" or "xAI" names. `vktr` is a rebrand by design, so this is a
requirement we already meet. No CLA is offered or needed.

**Build reproducibility.** Toolchain pinned by `rust-toolchain.toml` (Rust 1.94.0, stable).
Two git dependencies, both public: `our-forks/async-openai` (fork of `64bit/async-openai`,
MIT) at a pinned rev, and `helix-editor/nucleo` at a pinned rev. `bin/protoc` is fetched
hermetically via DotSlash. Built on a Linux x86_64 host with
`cargo build -p xai-grok-pager-bin --release`: see "Build result" below.

**Provider extension surface.** Grok Build already abstracts the model backend:

- `ApiBackend { ChatCompletions, Responses, Messages }` in
  `crates/codegen/xai-grok-sampling-types/src/types.rs`, with one stream parser each in
  `crates/codegen/xai-grok-sampler/src/stream/{chat_completions,responses,messages}.rs`.
- `[model.<name>]` config entries carry `base_url`, `api_key`, `env_key`, `api_backend`,
  `context_window`, etc.; a custom endpoint mode (`GROK_MODELS_BASE_URL`) discovers models from
  `{base}/models` (`crates/codegen/xai-grok-shell/src/agent/config.rs`).
- Auth: when an API key is present the `xai.api_key` auth method comes first and
  `startup_auth_metadata()` returns `needs_login = false`
  (`crates/codegen/xai-grok-pager/src/acp/mod.rs`), so no xAI account is needed.
- The sampler already types "the model returned nothing" as
  `SamplingError::EmptyResponse` with retry classification (`xai-grok-sampler/src/retry.rs`),
  which is where Viktor's `run_failed` error class maps.
- Home/config directory is resolved in one crate (`crates/codegen/xai-dirs`,
  `$GROK_HOME` or `~/.grok`), so `~/.vktr` is a single-crate change.

**Costs and risks.**

- Heavy: ~83 MB of Rust across 162 crates, a full release build takes tens of minutes and
  ~160 MB of binary. Incremental builds are fine.
- Hard-coded xAI surfaces to neutralise: `api.x.ai`, `auth.x.ai`, device-code login, telemetry
  (Mixpanel/OTel with build-time keys), auto-update, promo/ToS links (~250 string occurrences).
  These are removed or made no-ops, not merely hidden.
- Brand footprint: ~500 source files mention "Grok"; the user-visible ones are rebranded, the
  internal crate names are left as-is to keep upstream diffs reviewable.
- Root `Cargo.toml` is generated upstream; we edit it anyway (we own the fork).

## Evidence: Viktor API

The public Viktor compat API (`https://api.viktor.com/api/compat/v1`):

- `POST /v1/chat/completions`, `POST /v1/responses` (`previous_response_id` resumes the thread
  it names), `POST /v1/messages`, `GET /v1/models` (single model id `viktor`),
  `POST /v1/messages/count_tokens`.
- Auth: `Authorization: Bearer <key>` or `x-api-key`; the key needs the `chat:completions` scope.
- Tools: caller tools round-trip on all three protocols, interleaved with Viktor's own tools; a
  caller tool name wins on collision.
- Images: `image_url` parts (data: or https).
- A failed or empty run is never an empty `finish_reason: stop`. Non-streaming: HTTP 502 with
  `{"error": {"type": "server_error", "code": "run_failed", ...}}`; streaming: one
  `data: {"error": ...}` frame then `[DONE]` (Chat Completions), an `error` event (Messages), or
  `response.failed` (Responses).

All three Viktor protocols map 1:1 onto Grok Build's three `ApiBackend`s. The Responses
backend is the natural default for Viktor because it is the only one with server-side
continuation (`previous_response_id`).

## Evidence: OpenCode (fallback)

`anomalyco/opencode` (MIT, TypeScript on Bun, TUI in `packages/tui`, providers via the Vercel
AI SDK in `packages/opencode/src/provider`). Cheaper to modify and to build, and it already
runs against OpenAI-compatible backends. It is a viable fallback, but Grok Build is not blocked,
and the brief prefers it.

## Decision

Fork **Grok Build at `9bb727cc`** as `vktr`.

- Vendor the tree as the first commit, keep `LICENSE` and `THIRD-PARTY-NOTICES`, add `NOTICE`
  stating the origin and that the work is modified.
- Rebrand: binary `vktr`, home `~/.vktr` (`VKTR_HOME`), config `~/.vktr/config.toml`,
  sessions under a workspace-specific directory, no xAI login/telemetry/update/promo paths.
- Add a `viktor` provider kind on top of the existing backend abstraction: API key + base URL
  config, Responses backend by default with `previous_response_id` continuation, Chat
  Completions/Messages selectable, remote Viktor tools surfaced as such, `run_failed` and
  in-stream error frames surfaced as errors (never as an empty reply).
- Keep the generic OpenAI-compatible `[model.*]` provider so `vktr` runs against local backends
  (Harbor, Ollama, llama.cpp).

## Build result

Built on 2026-09-20 on a Linux x86_64 host (16 cores, Rust 1.94.0,
DotSlash 0.5.7) from a fresh shallow clone at `9bb727cc`:

```
cargo build -p xai-grok-pager-bin --release -j 14
Finished `release` profile [optimized] target(s) in 8m 39s   (66 min CPU)
target/release/xai-grok-pager   231 MB   -> reports "grok 1.0.38 (4247f6616893)"
```

Zero warnings, zero errors, no network access beyond crates.io, the two pinned git
dependencies and the DotSlash-fetched `protoc`. The default `release` profile is not the
hardened `release-dist` profile upstream ships (thin LTO, ~2.2x slower), which explains the
larger binary than the installed 160 MB `grok 1.0.30`.

Smoke test, headless, against a local mock OpenAI-compatible server (`/v1/models` +
streaming `/v1/chat/completions`), with a throwaway `GROK_HOME`:

```
[model.mock]                      # GROK_HOME/config.toml
model = "mock-model"
base_url = "http://127.0.0.1:8765/v1"
env_key = "XAI_API_KEY"

XAI_API_KEY=mock-key xai-grok-pager -p "Reply with the single word hello." -m mock
MOCK_OK: hello from the mock endpoint.      (exit 0; mock saw Bearer mock-key, stream=true)
```

Two findings that shape M1: (1) `XAI_API_KEY` + `GROK_MODELS_BASE_URL` alone is not enough
for headless mode, the model must be declared under `[model.*]` with `env_key`/`api_key`,
otherwise the headless auth gate reports "Not signed in"; the `viktor` provider must therefore
register its model as a built-in so no user config is needed. (2) A fresh home directory gets
`README.md`, `docs/`, `managed_config.lock`, `models_cache.json` written on first run; the
managed-config and update paths must be cut in the fork.

## Consequences

- We inherit a mature TUI, tool set, session store, MCP, ACP and headless modes on day one; the
  work is rebranding, de-xAI-ing and the Viktor provider, not building a TUI.
- Upstream does not accept PRs, so fixes stay in our fork. Upstream updates are merged, not
  re-copied. `scripts/upstream.py` snapshots each upstream sync onto `vendor/grok-build`
  (byte-identical) and `vendor/grok-build-rebranded` (`scripts/rebrand.pl` applied, minus
  `scripts/rebrand.exclude`). `main` merges the rebranded branch, so an update replays only what
  upstream changed and conflicts only where vktr changed the same lines. The procedure is in
  `.agents/skills/update-upstream/SKILL.md` (added 2026-09-29, when `main` was linked to the
  `9bb727cc` base).
- Anyone distributing `vktr` binaries must ship the Apache-2.0 LICENSE, NOTICE and
  THIRD-PARTY-NOTICES with them.
